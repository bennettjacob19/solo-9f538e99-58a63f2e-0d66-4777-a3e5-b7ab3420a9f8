# 窄带组播补传演练

站台终端在窄带组播中漏收绕行图，本网页用于本地补传演练。

## 玩法

1. **上传新图**：按 4 KiB 切块，至多 8 块（即 ≤ 32 KiB），末块补零、重组按原长截断。
2. **登记终端**：启用 2~4 台，勾选每台首播实收的块号。
3. **逐轮补传**：每轮设定广播帧数上限和各终端的异或解码额度。一帧发一个
   原块或两块异或；终端实收异或帧、恰缺一块且解码额度未用完时才解回缺块。
   按本轮无丢帧推算，限额内各站都能收齐才选一套方案发送，否则报无方案并
   保留已收块。可注入某台终端漏收本轮某帧。
4. 页面列出实发帧、各站缺块与解码次数；下一轮按各站实收和解回的块继续补传。
5. 每台终端独立拼图，SHA-256 与新图相符才替换可下载的旧图。
6. **漏帧回报更正**：值班员可在网页选终端和已发送轮次，把该轮改记为全收或漏收
   其中一帧。实发原始帧记录保留不变，所选轮同时展示该站的原回报与当前登记；
   系统以首播实收为起点，按各轮实发帧序、原解码额度和当前漏帧登记重算该站的
   缺块与累计解码次数。更正后未收齐的站恢复下载旧图，收齐且通过 SHA-256 校验
   才供新图；其他站的进度与下载完全不变，下一轮按更正后的缺块规划。校验失败时
   收帧登记、进度和下载图保持原样。

## 更正重算为什么不随历史轮数线性增长

- 一轮对某站的作用只取决于该站进入本轮时的块掩码（解码计数每轮从零起算），
  因此每轮被抽成一张至多 `1 << 块数`（≤256）项的转移表：入口掩码 →
  (出口掩码, 本轮解码次数)。建表只回读该轮自己的实发帧记录。
- `progress.py` 用分层段树（`seg[k][j]` 覆盖轮次区间 `[j·2^k, (j+1)·2^k)`）
  复合各轮转移表：发新轮追加 O(log 轮数) 个段；更正一轮只重建该轮叶表及其
  祖先链，也是 O(log 轮数) 次定长表复合；查询当前状态同样 O(log 轮数)。
  单表大小只取决于块数（≤8），与历史轮数无关。

## 启动

```bash
docker compose up --build      # 或：pip install -r requirements.txt && python app.py
# 打开 http://localhost:5000
```

## 测试

```bash
python -m pytest tests/ -q
```

## 结构

- `planner.py`：切块/重组、BFS 帧序列规划（限帧数+限解码）、轮次/单站执行（含漏帧注入）
- `progress.py`：轮次转移表与分层复合索引，支撑 O(log 轮数) 的更正重算
- `app.py`：Flask 页面、状态流转与漏帧回报更正
- `templates/index.html`：单页界面
- `tests/test_drill.py`：切块、紧额度、漏帧补传、全流程测试
- `tests/test_correction.py`：索引对拍、复杂度断言、更正全流程与失败回滚测试
